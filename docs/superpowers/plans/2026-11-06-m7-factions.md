# M7 Three Factions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task (native, sequential, per `prompt.txt`). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** USA, China and FRC play like their Zero Hour counterparts through capability data, offline against the skirmish bot and online between two players, ending in a deterministic headless 3v3 bot match on Ashfall with all three factions.

**Architecture:**
- **Performance first.** Trace-preserving fixes bring the over-budget simulation rows down before faction cost is added.
- **Capability data.** Kinds live in one typed GDScript file per faction plus shared tables. Systems read capability fields and never a faction id; a faction table holds start setup and bot data only.
- **Rename before rules.** A pure rename to `usa_*` ids keeps every core series and terminal tick. Capability reads then replace kind literals, still behaviour-preserving. Only after that do behaviour changes start.
- **Match start.** Each seat has a `faction`. Offline, `Skirmish.create` sets factions up directly. Online, each seat sends `choose_faction` as its first lockstep command (tick 4); relay and `protocol/` stay unchanged.

**Tech Stack:** Godot 4.7.2, typed GDScript, Python 3 stdlib, `sh tools/run_tests.sh`, `sh tools/run_benchmark.sh`, `sh tools/run_team_match.sh`, `sh tools/run_profile.sh`, `sh tools/run_netplay.sh`, `sh tools/run_conformance.sh`, `tools/zh_parity/`.

## Code anchors and pitfalls

Register new suites in `SUITES` in `game/tests/run_tests.gd`. Python tool tests use `unittest` (`python3 tools/<file>.py`). A GDScript test never reads `.gd` source.

## Global Constraints

**Units.** 1 cell = 25 Zero Hour units; 1 tick = 1 frame (30 Hz). Distances, speeds, accelerations ÷ 25; build seconds × 30; HP and damage × 1000; cost and power as-is; armor % per damage type, 100 when unlisted. Radius: cylinder `major / 25`, box `sqrt(major² + minor²) / 25`. Weapon delay `ceil(ms × 30 / 1000)`, replaced by the measured value from Task 2 when that is within ±1.

**Ids (fixed at Task 3).**
- Factions are `usa`, `china`, `frc`. Kinds are `<faction>_<role>`.
- Unit roles: `builder`, `collector`, `rifle_infantry`, `rocket_infantry`, `light_vehicle`, `tank`. `frc_builder` also collects, and there is no `frc_collector`.
- Building roles: `command_center`, `power_plant` (none for FRC), `supply_center`, `barracks`, `factory`, `defence`, plus `frc_hole`.
- Task 3 mapping:
  - kinds: `builder→usa_builder`, `collector→usa_collector`, `vehicle→usa_light_vehicle`, `infantry→usa_rifle_infantry`, `tank→usa_tank`, `reactor→usa_power_plant`, `depot→usa_supply_center`, `barracks→usa_barracks`, `factory→usa_factory`;
  - armor keys: `dozer→builder_vehicle`, `humvee→light_vehicle`, `chinook→helicopter`, while `human`, `tank` and `structure` stay;
  - map slot keys become the role: `reactor→power_plant`, `depot→supply_center`, while `barracks` and `factory` stay.
- Locomotor values (`wheels`, `legs`, `treads`, `air`) and weapon ids (`rifle`, `cannon`) do not change.
- No EA or product name (Humvee, Patriot, Chinook, Red Guard, Scorpion, Dozer, …) in ids, data, UI or maps.

- `definitions/usa.gd` holds `const KINDS := {id: {...}}`: economy fields, the combat profile fields `max_hp`, `armor` and `weapon`, and capabilities.

**Capability fields** (added only by the task that first uses them):
- All kinds: `display_name`.
- Units:
  - `class`: `"infantry"`, `"vehicle"` or `"air"`;
  - `radius`, `vision`, `builds: Array[String]`;
  - `collects: {boxes, load_ticks, unload_ticks, box_value}`; Task 4 moves today's 8 / 36 / 87 / 75 there;
  - `contains: {slots, accepts: Array[String], passengers_fire: bool, passenger_damage_percent: int}` (Task 9).
- Buildings:
  - `produces: Array[String]` (replaces the unit's `producer`);
  - `receives_supply: bool`, `counts_for_victory: bool`, `slot: String`;
  - `spawns_on_complete: Array[String]` (Task 4);
  - `powered: bool` (Task 10).
- The gates add `quantity`, `horde`, `ramp`, `salvage`, `weapon_tiers` and `rebuild_hole`.

**Survival (Zero Hour).** `_survives(p)` is true when `p` owns any building record, foundation or completed, whose kind has `counts_for_victory`. Units never count. The flag is true for command_center, power_plant, supply_center, barracks, factory and `frc_hole`, and false for every defence.

**Match start.**
- Seat dict gains `faction: String` (Task 5).
- `Simulation.setup_seat(player: int, faction: String) -> void` (Task 5):
  - sets the seat's faction;
  - places `start_building` completed at slot `command_center`;
  - spawns `start_unit` at `start_cell + 0.5`.
- `Skirmish.create(with_match: bool = true, second_controller: String = "ai", factions: Dictionary = Factions.DEFAULT_SKIRMISH)` calls `setup_seat` per seat, then `start_match`.
- With `factions == {}` (online, Task 6) it calls `begin_setup(players)`, which sets `_match = {players, status: "setup", winner: null, ended_tick: null}`.
- **`match_over()` becomes `_match != null and _match.status in ["won", "draw"]`** (Task 6). `_evaluate_match` is skipped while the status is `setup`.
- `choose_faction {faction: String}` (Task 6):
  - validation: "Unknown faction" if the faction is not in `FACTIONS`, "Faction already chosen" if the seat's faction is set;
  - applying it calls `setup_seat`;
  - when the last seat has chosen, `start_match` runs at the end of `_apply_orders` that same tick;
  - while the status is `setup`, any other command from a seat without a faction is rejected with "Choose a faction first".

**Snapshot fields added at gate 1 (exactly these):**
- `players[].faction` (Task 5);
- `match.status` value `"setup"` (Task 6);
- entity `container_id: int` only while inside a container (key absent otherwise; as built, Task 9: a key on every entity would move every full-snapshot trace);
- container entity `passengers: Array[int]` in id order, only while loaded (key erased when empty; the enter intent lives in `unit.order`, no `enter_id` key);
- building `combat` record on armed completed buildings (Task 10).

Anything else needs a design question.

**Determinism.** No banned math in `game/scripts/simulation/` (`tools/test_sim_math.py`). Randomness only from `sim.next_random()`. Iterate in id order wherever order affects state.

**Pins and windows.**
- Nothing relaxed. Tasks 1, 3 and 4 move no core series (`S1_CORE_SERIES`, `TEAM_CORE_SERIES`), terminal tick or netplay tick.
- Task 3 alone may move the digests (`PINNED`, `FINAL_DIGEST`) and the definition-dict pins; cause "rename".
- Tasks 5–10 re-pin provisionally what their own change moves. Windows (user 2026-11-06):
  - S1: `TICK_LIMIT` 18000, window 8000–17999 (`test_skirmish_match.gd:100`), winner 1;
  - team match: `TEAM_TICK_CAP` 45000, result `won`;
  - netplay `match`: same winner, within the script's limit;
  - BM6 floor stays below the measured value.
- Leaving a window is a stop.
- **Allowed test-setup change (Task 5).** Tests that started a match with builder-only seats get a completed counting building through the new test helper `EconomyFixture.add_completed(sim, owner: int, kind: String, origin: Vector2i) -> int`. It inserts the building record with `completed = true`, in the same shape as `Construction.place`. Each changed test is listed in the verification file.

**Out of scope:** other units, aircraft combat, superweapons, upgrades, veterancy, stealth, travelling projectiles, minimum range, the missile battery's assist weapon (departure, recorded), smarter bots, fog, Generals HUD, playing on Ashfall, more than two online seats.
