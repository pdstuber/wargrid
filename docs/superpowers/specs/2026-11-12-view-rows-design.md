# View rows: design (2026-11-12)

Status: **proposed, waits for stop gate 2 (user approval). Not started.** Revised 2026-11-11 after the architecture review with the user's decisions (HUD columns instead of `details`, T4b, table indices, RF and plumbing answers). Task T4 of the [performance next plan](../plans/2026-11-11-performance-next.md). Written against `perf-next` at bed2e7b (T1 clock and T3 rows in the tree, two RF tests being added uncommitted). Read-only design; no Godot process was run. Numbers come from the T3 rows in `docs/reference/performance-next-verification.md` (measured, probe copy of 577ca06). Lever C of the [performance note](../../reference/performance-next.md) (section 6), hot spots H3-H6 (section 3).

Rules: no simulation behaviour or trace change, typed GDScript, no generic framework, [determinism rules](../../reference/determinism-rules.md). Pass (plan): the game scenes no longer call `snapshot()` once per tick; the plumbing row improves by more than its spread on every layout; suite, pins and netplay unchanged.

## Decisions

1. **The simulation owns the rows, and builds them fresh on every call.** New `Simulation.view_state()` (no parameters) returns the small records the presentation reads plus `units`, a `ViewRows` object with packed columns. Only the simulation reads `_entities`, in place and never through `_entity_copy`, so the call changes nothing in the simulation (no route is frozen). T5's worker will publish exactly this object per tick. Fresh packed arrays per call (about 20 allocations per tick, none per unit) need no double buffer and cannot be changed under a holder. Rejected: rows kept up to date by each system as they write (that is lever D1, touches every system, needs the golden scenarios first).
2. **Dense columns, one row per unit, id order.** Not per-kind arrays: drawing, picking and HUD all address "unit i", the depth sort covers every unit at once, and per-kind arrays would need a merge for both. Kind is an index into a per-call `kinds` table.
3. **The view keeps one item Dictionary per unit across ticks and rewrites its fields from the rows.** `WorldBatch.build`, the visual director and the pose code keep reading item Dictionaries, unchanged, so the golden batch test (WB18) stays green with its digest untouched and exercises the new path. A new Dictionary is made only when a unit appears. Rejected for now: `build()` reading rows directly. It saves the remaining in-place writes (estimate 0.06-0.26 ms, see Gain) but rewrites the golden path. It is a presentation-only follow-up, **T4b** (`build()` and the pose code read rows directly), planned after T4's numbers and decided by the user then; task 7 measures how much of `view.build` and `view.poses` is Dictionary reads, so T4b starts from a number (user, 2026-11-11).
4. **One `set_state` shape for tests, one for the game.** `WorldView.set_view(view, selected)` is the game path. `set_state(snapshot, selected)` stays and converts with `ViewRows.from_units(state.entities)`, so the 89 `set_state` calls in `test_view.gd`, the art lab and anything snapshot-shaped run through the same row code. `from_units` is also what the simulation calls on its live units: one fill function, no second reader.
5. **Every scene refresh reads `view_state()`, per tick and on input.** `_refresh()` never takes a snapshot. Input handlers that need full unit fields (`_matching_ids`, `_builder`, `_context_order`, `_container`, `_enemy_at`, `_unload_selected`, `_submit`'s `last_sequences`) keep their own `snapshot()` call, as today.
6. **HUD fields as columns.** Beyond the drawing columns the HUD reads four unit fields: `combat.mode`, `combat.target_id`, `collection.enabled`, `collection.phase` (`skirmish_main.gd:180-211`). They are the `mode` and `phase` byte columns (indices into per-call `modes` and `phases` tables, the `kinds` pattern), the `COLLECTING` flag and the existing `target`; the line position uses the existing `queue` (section 2). Rejected (architecture review, user 2026-11-11): snapshot-shaped `details` copies for chosen ids, because `_entity_copy` freezes the live unit's route (`simulation.gd:592-597`), so `view_state()` would change simulation state depending on the selection, which VR4's digest cannot see. Rejected: a `simulation.unit(id)` query, because under T5 the HUD must not read the live simulation.
7. **No veterancy column.** The simulation has no veterancy field (`rg veterancy game/scripts/simulation` finds only a comment in `salvage.gd:41`). The per-frame chevron loop in `_draw_lines` (`world_view.gd:421-424`) never draws and is removed; `veterancy_lines(unit)` and its test V24 stay as the art placeholder. When the simulation gains veterancy, that change adds a `veterancy` byte column.

## 1. Row columns and owners

`game/scripts/simulation/view_rows.gd`, `extends RefCounted`, built by `Simulation.view_state()` (owner) and by `ViewRows.from_units()` (tests, labs). Typed members, all of length `size()`, row `i` is one unit, rows sorted by id. Defaults are those `WorldBatch.objects` / `_item` use today (`world_batch.gd:91-119`), so hand-built test units without a field keep working.

| Column | Type | Source field (unit Dictionary) | Default | Readers |
|---|---|---|---|---|
| `id` | `PackedInt32Array` | `id` | | everyone; `index_of(id)` is `id.bsearch` |
| `owner` | `PackedInt32Array` | `owner` | 0 | batch, picking, HUD, sound |
| `kind` | `PackedInt32Array` | index of `kind` in `kinds` (`PackedStringArray`, built per call) | `""` | batch role/layer, bounds, picking, HUD, sound |
| `hp`, `max_hp` | `PackedInt32Array` | `hp`, `max_hp` | 0 | batch, health bars |
| `target` | `PackedInt32Array` | `combat.target_id` | -1 | batch, visual director aim, focus boxes, HUD |
| `queue` | `PackedInt32Array` | `collection.target_id` while `collection.phase` begins with `waiting_` | -1 | HUD line position (`line_position`) |
| `x`, `y` | `PackedFloat64Array` | `position` | | everyone |
| `heading_x`, `heading_y` | `PackedFloat64Array` | `heading` | `[1.0, 0.0]` | batch (`atan2` stays in presentation: no trig in the simulation folder) |
| `order_x`, `order_y` | `PackedFloat64Array` | `order.target` | 0.0 | order marks |
| `status` | `PackedByteArray` | index of `status` in `STATUSES = ["moving", "path_pending", "arrived", "blocked", "idle", "contained"]` | 255 for any other value | `main.gd` HUD counts |
| `tier` | `PackedByteArray` | `combat.tier` | 0 | sound (weapon cue) |
| `mode` | `PackedByteArray` | index of `combat.mode` in `modes` (`PackedStringArray`, built per call) | 255 (`NONE`) without combat | HUD |
| `phase` | `PackedByteArray` | index of `collection.phase` in `phases` (`PackedStringArray`, built per call) | 255 (`NONE`) without collection | HUD |
| `flags` | `PackedByteArray` | bit constants below | 0 | as named |

Flags: `HORDE` (`combat.horde > 0`, batch ring), `CONTAINED` (has `container_id`, picking), `HOLE` (has `hole_id`, picking), `ATTACKING` (`combat.mode == "attack"`, focus box width), `ORDERED` (`order != null`, order marks), `WAITING_SOURCE` (`collection.phase == "waiting_source"`, pile labels via `_waiting_counts`), `COLLECTING` (`collection.enabled`, HUD collection suffix).

The two collection fields T3 found missing are covered by `WAITING_SOURCE` plus `queue`; the HUD's phase string comes from `phase`. Veterancy: decision 7. Rows carry no `route`, `destination`, `speed`, `passengers` or `combat` record; nothing per tick reads them.

**Table indices.** `kind`, `mode` and `phase` are valid only together with the same rows object's own `kinds`, `modes` and `phases`: the tables are built per call, so one index can name different strings on two ticks. Code that holds two rows objects (the sound director keeps the previous tick's) compares strings, or looks each index up in its own rows' table; it never compares indices across rows objects. `from_units` asserts each table stays below 255 entries, so `NONE` never names a string.

`view_state() -> Dictionary` keys: `tick`, `map` (shared read-only, as in the snapshot), `players` (`_player_snapshots(true)`), `buildings`, `sources` (`_sorted_copies`), `match`, `command_results`, `crates` when any exist, all with the snapshot's values; `units`. Not included: `entities`, `pending_commands`, `last_sequences`, `path_queue`, `terrain_cells`, `next_*`, `rng`, `combat_events` (the directors get events through `collect_step`). Profiler zones: `view_state` around the whole call, `view_rows` around `from_units`, so the record copies show as the difference.

It is not a state fingerprint and holds an `Object`, which the snapshot rules forbid (determinism rules, "Snapshot values"); it never goes into `StateHash.digest` or a desync report.

## 2. Consumers

### `world_view.gd`

`_state` becomes the view state (from `set_view`, or converted in `set_state`). The shallow `state.duplicate()` (`view.copy`) goes: nothing reorders the caller's data any more. New members: `_order: PackedInt32Array` (row indices in today's depth order, built per tick by `WorldBatch.depth_order(units)` with the same key as `depth_sorted`, `world_batch.gd:132-144`, which it replaces), `_unit_items: Array[Dictionary]` (id order). Every loop that today walks `_state.entities` walks `_order` instead, so draw order, pick priority and Dictionary insertion order of the results stay as they are. `_drawn_position(unit)` becomes a lookup by row (`_drawn.get(id, Vector2(x[i], y[i]))`); `_vehicle_bounds`, `_pick_bounds`, `_ground_diamond` take kind and point instead of a unit Dictionary.

| Function (line today) | Rate | Reads after T4 |
|---|---|---|
| `set_state` / new `set_view` (179) | tick | rows: `_order`, unit items (merge walk below), structure items |
| `_remember_points` -> `_points_of` (569, 578) | tick | rows by `index_of` for wanted ids; buildings unchanged |
| `_refresh_structures` -> `_waiting_counts` (455, 544) | tick | `WAITING_SOURCE` and `queue` |
| `_draw_rects` health bars (404) | frame | `hp`, `max_hp`, kind, drawn point |
| `selected_unit_lines` (137), `order_marks` (340) | frame | rows; `ORDERED`, `order_x/y`, `owner` |
| `_draw_lines` chevrons (421) | frame | removed (decision 7) |
| `focus_targets`, `_draw_focus` (475, 484) | frame | `target`, `ATTACKING`, bounds |
| `_draw_inspected` (500), `resume_candidate` (309) | frame, and per HUD refresh | rows (`owner`, kind) |
| `pick_target`, `pick_entity`, `pick_entities`, `pick_object` (362, 373, 593, 610) | input | rows in reverse `_order`; `CONTAINED`, `HOLE`, kind |
| `pile_lines` (538) | per label | `_waiting_counts` on rows |
| `horde_count` (351) | overlay | items, unchanged |

No `world_view.gd` consumer needs a snapshot. Unit items: `_items` = unit items followed by today's building and source items (still built fresh, they are few). Order inside `_items` does not matter: `build()` sorts by layer, depth and id; `_track_poses`, `_apply_alpha` and the visual director key by id.

Merge walk, once per `set_view` (ids only ascend, so one pass):

```gdscript
var next: Array[Dictionary] = []
var j: int = 0
for i in units.size():
	var id: int = units.id[i]
	while j < _unit_items.size() and _unit_items[j].id < id: j += 1
	var item: Dictionary = _unit_items[j] if j < _unit_items.size() and _unit_items[j].id == id else {}
	next.append(WorldBatch.write_unit_item(item, units, i))
_unit_items = next
```

`WorldBatch.write_unit_item(item, units, i) -> Dictionary` fills an empty item with all 16 keys of `_item`, and on every call writes `owner`, `anchor`, `heading` (`atan2(heading_y, heading_x)`), `target_id`, `hp`, `max_hp`, `horde`; `role`, `layer` and `shadow` are rewritten only when `item.kind` differs from the row's kind. `WorldBatch.objects(state)` becomes `write_unit_item` over `ViewRows.from_units(state.entities)` plus `structure_items(state)` (today's building and source part), so WB18 runs the new code. The order inside `set_view` stays today's: items, `_track_poses`, `_apply_alpha(_alpha)`, visuals update, `_rebuild_batch`. T3's sub-zones (`view.objects`, `view.poses`, `view.visuals`, `view.build`) become permanent inside `view.batch`; T6 needs them.

### Scenes

- **`main.gd` `_refresh` (223)**: `_show(simulation.view_state())`.
- **`main.gd` `_show` (226), selection pruning (H6)**: keep the selected ids for which `state.units.index_of(id) != -1`; no per-tick id list, no linear search. Overlay count from `units.size()`.
- **`main.gd` `_refresh_hud` (248)**: status counts from the `status` column.
- **`base_main.gd` `_refresh` (67)**: same view state; building checks on `state.buildings` unchanged. `_menu_kinds` (91): the selected unit's kind through `index_of`. `_refresh_hud` reads `command_results`, `players`, `buildings`, `tick`: all in the view state.
- **`skirmish_main.gd`** (HUD texts unchanged, pinned by HUD1): new `_unit_record(units, i) -> Dictionary` builds the snapshot-shaped subset the HUD formats: `id`, `owner`, `kind` (through `kinds`), `hp`, `max_hp`, `combat` (null when `mode` is `NONE`, else a Dictionary with `mode` through `modes` and `target_id` from `target`, null for -1), `collection` (null when `phase` is `NONE`, else a Dictionary with `enabled` from `COLLECTING` and `phase` through `phases`). At most two per HUD refresh, never per unit.
  - `_inspected(state)`: `state.units.index_of(inspected_id)` first, then `buildings` (today's entities-then-buildings order); a unit returns `_unit_record`, a building its record as today. `_refresh_hud`'s `_inspected(state).is_empty()` check is unchanged.
  - `_selected_summary`: finds the single selected unit with `index_of` and `_unit_record`; its formatting lines stay as they are. `_enemy_summary`: unchanged (it reads `_inspected`).
  - `_collection_suffix(state, unit)`: the phase string from the record; `View.line_position(state.units, state.units.index_of(unit.id))` counts rows with a lower id and the same `queue` as the unit's own row, plus one. It runs only while the unit's phase begins with `waiting_`, so its own `queue` is its `collection.target_id` (column rule, section 1), and another row has that value only while it waits on the same target: today's predicate (`world_view.gd:551-555`, which also skips units without collection, `queue` -1). A waiting phase is set only at a chosen target (`supply_collection.gd:140-152`), so the unit's `queue` is never -1 there.
- **`online_main.gd`**: `_refresh` inherited. `_lockstep.start(snapshot)` (once) and `finish_tick(tick, snapshot if wants_snapshot)` (hash ticks) unchanged.
- **Picking**: unchanged callers; the view's pick functions read rows.
- **Sound director** (`sound_director.gd:53-99`): `update(state)` takes the view state. `_records` builds records for buildings only; unit lookups (`_lookup` for shot attacker and target, death, `_last_shot` cleanup, `_unit_ready`) use `index_of` on the current rows, then on the previous tick's rows, and build a small record only for an id an event names, reading `kind` through the `kinds` of the rows object the row came from (table indices, section 1); kinds from the two ticks are compared as strings. No per-unit Dictionary per tick (today it makes one per unit per tick).
- **Visual director**: no change. It reads the unit items, which now persist; its `_anchors` stores `Vector2` values, not item references.

## 3. The split clock

No change to `presentation_clock.gd`. The clock decides when `_refresh()` runs; `_refresh()` now builds the view state instead of a snapshot, at the same moment. When the split is active, the refresh frame gets lighter by the gain below; the step frame is unchanged. Two steps in one frame still show the newer tick, as today. RF3 and RF5 read `_view._state.tick`, which the view state carries, so they stay as written. For T5: the view state is the hand-off unit. The remaining main-thread reads of the live simulation after T4 are `tick()` (clock), `combat_events()` / `command_results()` in `_collect_sound`, `team_of`, `match_over`, `preview_build` and the input-event snapshots; T5 owns them.

## 4. Test plan

Every new test uses only the simulation interface (after section 6's update) and public view functions. `tools/test_sim_boundary.py` enforces it.

- **VR1, characterization, written first on the unchanged tree.** New `game/tests/test_view_rows.gd`. Two real states: `Skirmish.create()` with bots stepped to tick 3000, and `CombatWorkload.create("hordes300")` at tick 400. For each, a fixed selection (the first 5 own units, one collector, one builder), fed through `set_state(sim.snapshot(), selection)`. Hash into one SHA-256: `WorldBatch.objects(snapshot)` built at detail 1 with shadows (points and colours), `selected_unit_lines()`, `focus_targets()` (keys and values in order), `order_marks()` with destinations on, `pick_entities` over the whole map, `pick_entity` and `pick_target` at five unit anchors, `pile_lines` per source, `resume_candidate()`, `horde_count()`. Record the digest as a constant on HEAD (run twice, same value). From task 2 on, the same constant must hold, fed through `set_view(sim.view_state(), selection)` as well as `set_state`. A moved digest is a bug in the task, never re-recorded.
- **VR2, rows equal the snapshot on real data.** Six states: hordes300 at ticks 40, 400, 1500 (T3: targets only appear late), the skirmish at 3000, a team-match prefix at 2000 (`TeamMatch.create`), and a transports fixture from `test_benchmark.gd`'s `test_transports_fixture` setup. For every unit, a reader written in the test, not `from_units`, compares each column with the snapshot entity field by field (`==` on floats and ints), kind, mode and phase through their own tables, every flag bit. Coverage checks fail on zero: at least one unit per state set with a target; across all states at least one each of `HORDE`, `CONTAINED`, `ATTACKING`, `ORDERED`, `WAITING_SOURCE`, `COLLECTING`, a `queue` value, a non-zero `tier`, a `mode` other than `guard`, a `phase` beginning with `waiting_`, and `NONE` in `mode` and in `phase`. If a bit has no unit in these states, the task extends a state, it does not drop the check.
- **VR3, the other keys.** `view_state()[k] == snapshot()[k]` for every key of section 1 except `units`; the view state has no key outside section 1's list.
- **VR4, read-only and independent.** `StateHash.digest(sim.snapshot())` is equal before and after a `view_state()` call. Two sims built the same way (the skirmish with bots): A calls `view_state()` before each of 300 steps, B never does; their digests are equal every 30 ticks and at the end. A held view state is unchanged after 30 steps (compare against a deep copy of its records and a copy of each column and table). Route read-only flags: see the open question below this list.
- **HUD1, HUD texts pinned, written first on the unchanged tree.** In `test_skirmish_scene.gd`, on the VR1 skirmish state: the full `_selected_summary(state)` text for a single selected combat unit with a target, a collector in a `waiting_` phase with at least one lower-id unit waiting on the same target (so the ordinal is not `1st`), an enabled collector not waiting, and an own unit without combat if the state has one; the full `_enemy_summary(state)` text for an inspected enemy unit with combat and for an inspected enemy building. Expected texts are literal strings recorded on HEAD with `sim.snapshot()`; from task 5 on the same strings must come from `sim.view_state()`. Each case fails if its unit is missing (extend the state, never drop the case). A moved text is a bug in the task, never re-recorded.
- **VR5, items persist.** Two `set_view` calls one tick apart: the same unit's item is `is_same` in both; a removed unit's item is gone; a spawned unit gets one; an item's `anchor` after the second call is the new position, not an interpolated leftover.
- **Golden batch, WB18** (`test_world_batch.gd:235`): unchanged, expected digest `412a2fbb...` untouched; it now goes through `from_units` and `write_unit_item`.
- **Per consumer that changes:** `test_view.gd` keeps every expected value; one case changes its access only (`test_view.gd:180` reads `_state.entities` for the depth order; it reads `_order` and `units.id` instead, same expected ids). Depth-sort tests of `depth_sorted` move to `depth_order` with the same expected order. Scene HUD: K4, S1 (line position) and E1 (inspection) keep their texts; K4's `main._refresh_hud(setup)` passes `view_state()` with the edited `match` instead of a snapshot. Selection pruning: add RF7 ("a dead selected unit leaves the selection, the others keep their order") if `rg` finds no existing case. Main scene counts: add one case for the `Moving / Pending / Arrived / Blocked` text if none exists. Sound: `test_sound.gd` and `test_announcer.gd` `_state` helpers add `units = ViewRows.from_units(entities)`; direct `sim.snapshot()` feeds become `sim.view_state()`; no expected value changes. `test_visual.gd`: unchanged. BM17 (`horde_camera`) builds rows with `from_units`.
- **Intended changes of expected values (list them in the verification row):** RF1 and RF2 (`test_base_scene.gd:253`, `test_skirmish_scene.gd:596`) assert `Profiler.calls(&"snapshot") == 1` per refresh; they become `== 0` with `Profiler.calls(&"view_state") == 1`, RF2's Produce label unchanged (user, 2026-11-11: yes). Reviewer, per test, names the change that makes it fail: VR1 a wrong depth key or a dropped pick filter; VR2 a column filled from the wrong field; VR4 a `view_state` that writes into a live unit or edits live state; HUD1 a `_unit_record` that gives a record instead of null for `NONE`, a phase or mode read through the wrong table, or a `line_position` that counts rows with `queue` -1; VR5 a merge walk that rebuilds items; RF6 a scene `_refresh` that snapshots.

**Open (user): the route read-only flag check.** The interface cannot see a live route's read-only flag without setting it: every `snapshot()` freezes all live routes (`simulation.gd:596`) and the copy shares the array. A direct flag check needs one private read of `sim._entities[*].route.is_read_only()` before and after `view_state()`, against "new tests use only the simulation interface" ([sim interface](../../reference/sim-interface.md)); if the user allows it, it goes into VR4 as a single exception named in the test.

## 5. Expected gain (per tick, ms, mean, headless `run_profile`)

"Hand-off" is T3's sum: `snapshot` + `view.copy` + `view.sort` + `view.batch` today; `view_state` + `view.sort` + `view.batch` after. The bound is T3's (measured parts, **a bound, not a design measurement**: it counts `view.objects` as zero and ignores the record copies). The estimate adds what this design keeps: in-place item writes and `atan2` (assumed 30-50 % of today's `view.objects`), five more columns than the probe (about +40 % of `view_rows`), and the building, source and player copies (not measured alone; T4 task 2's zones measure them).

**Plumbing row (proposal, user 2026-11-11: yes).** The ledger's plumbing row per layout is measured as the hand-off sum above: `view_state` or `snapshot` + `view.copy` + `view.sort` + `view.batch`, against the unchanged 0.91 ms budget. Task 7's ledger row states this definition as an explicit proposal; it does not change the budget. The rendered benchmark (`--zoom=0.5`, report-only) also loses the snapshot from `tick_ms`; per-frame draw loops read packed columns instead of Dictionaries, so `draw.units` may drop too (not estimated).

> - `ViewRows` (`view_rows.gd:<line>`): equal-length columns, row `i` is one unit. `PackedInt32Array`: `id`, `owner`, `kind` (index into `kinds`, a `PackedStringArray` built per call), `hp`, `max_hp`, `target` (`combat.target_id`, -1 for none), `queue` (`collection.target_id` while `collection.phase` begins with `waiting_`, else -1). `PackedFloat64Array`: `x`, `y` (`position`), `heading_x`, `heading_y` (`heading`, default `[1.0, 0.0]`), `order_x`, `order_y` (`order.target`, 0.0 without an order). `PackedByteArray`: `status` (index into `ViewRows.STATUSES`, 255 for another value), `tier` (`combat.tier`, 0 without combat), `mode` (index into `modes`, `ViewRows.NONE` = 255 without combat), `phase` (index into `phases`, `NONE` without collection), `flags` (`HORDE`: `combat.horde > 0`; `CONTAINED`: has `container_id`; `HOLE`: has `hole_id`; `ATTACKING`: `combat.mode == "attack"`; `ORDERED`: `order != null`; `WAITING_SOURCE`: `collection.phase == "waiting_source"`; `COLLECTING`: `collection.enabled`). `kinds`, `modes`, `phases` are `PackedStringArray`s built per call: a `kind`, `mode` or `phase` index is valid only with the same rows object's own table, so code holding rows from two ticks (the sound director) compares strings or looks up through each rows' own table, never indices across rows objects. `index_of(id) -> int` (binary search, -1 if absent). `ViewRows.from_units(units)` builds the same rows from snapshot entities in id order (tests, labs). A field the presentation needs per tick that is not a column becomes a new column in the same change, never a per-unit Dictionary again.

## 7. Risks

- **Stale reads.** A persistent item keeps any field that is not rewritten. Rule: `write_unit_item` writes every per-tick field on every call; kind-derived fields when the kind differs. VR5 and VR1 guard it. The HUD and the view read one view state per refresh; mixing it with live queries (`team_of`, `match_over`) sees the same tick as today, because no step runs between them.
- **Ordering.** Rows are in id order, today's entity list in the view was in depth order. Every loop that depended on that order walks `_order`; `_items` order is irrelevant to `build()` (total sort key) and to the id-keyed pose and visual code. VR1 hashes pick results and `focus_targets` key order.
- **Per-tick allocation.** Allowed per tick: the `ViewRows` object and its columns, one `kinds` table, the record copies the snapshot made anyway, one `_items` and one `_unit_items` Array, the existing pose and anchor Dictionaries. Not allowed: any Dictionary per unit per tick (the review checks `write_unit_item`, the sound director and `from_units`). Today there are three per unit (entity copy, its nested copies, the item) plus one in the sound director.
- **Route freezing.** `_entity_copy` makes a live unit's `route` read-only (`simulation.gd:596`); today every route is frozen every tick by the scene's snapshot, after T4 only on hash ticks and input events: `view_state()` reads live units in place and freezes nothing, whatever is selected. That would change behaviour only if simulation code edited a shared route in place; the only in-place edits are on the route being built (`simulation.gd:576-577`), and headless netplay clients (no per-tick snapshot) already agree with game clients. Guard: traces, pins, the netplay `match` scenario.
- **Table indices across ticks.** The same string can get a different index on the next tick. Rule and readers: section 1, "Table indices". The sound director is the only holder of two rows objects; HUD1, VR1 and the unchanged sound expected values guard it.
- **Int32 columns.** `id`, `hp`, `max_hp` and targets fit today (T3 compared them equal); VR2 catches an overflow.
- **Two entry points into the view.** `set_state` converts and `set_view` does not; both end in the same code, and VR1 runs both.
