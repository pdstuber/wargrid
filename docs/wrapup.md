# Wrap-up

End a Wargrid work day in any agent. Prepare the next `docs/kickoff.md`. `AGENTS.md` holds standing rules; this file sets check order.

1. Before any doc edits, so the tree is still clean: only when on a clean `main` and the newest `auto <sha>` label in `docs/reference/perf-history.csv` is not the last `main` commit that touched what the benchmark runs (`git log -1 --format=%h main -- game tools/run_benchmark.sh tools/perf_record.py tools/perf_chart.py`, the same pathspec as `MEASURED` in `tools/perf_record.py`), run `sh tools/run_benchmark.sh` (it records itself; [performance ledger](reference/performance.md)); if the load average is above 2.5, say so, or list the run for tomorrow. Otherwise list "benchmark main after the next merge" for tomorrow. Wrap-up never merges, so this applies to merges the user approved today. A record on `main` leaves `docs/reference/perf-history.csv`, `docs/reference/performance.md` and `README.md` modified for the user to commit.
2. Check local links and referenced paths in changed documentation, including `docs/kickoff.md`, this file and the session notes (`~/projects/wargrid-private/docs/session-notes.md`, outside this repository). Verify the session-note headings kickoff reads exist. No documentation-checker script currently exists; do not claim to have run one. Run `sh tools/check_public.sh` (public repository rule in `AGENTS.md`); it must pass. If simulation, presentation, net or relay architecture changed, update the affected chapter in `docs/guide/` and its `Checked against` footer.
3. If game code, tests, wrappers or engine configuration changed, run `sh tools/run_tests.sh` with output redirected to a file, reading only the summary lines (AGENTS test-output rule). Report case/check counts, exit status and diagnostics. If `relay/` or `protocol/` changed, run `go test -race ./...` and `golangci-lint run` in `relay/`, `sh tools/run_conformance.sh`, and the affected `sh tools/run_netplay.sh` scenarios. Run only affected additional checks; keep them headless. Documentation-only work needs link/path/status checks, not a game test run. Run `gh run list --branch main --limit 1` and report its conclusion; a red run, or none for the current code, is an open item, and unpushed work counts as unverified (push a `verify/<date>` branch to get a CI run; `main` still needs explicit approval). Complete the required single substantive review and final Ponytail pass for implementation work if not already done; do not repeat a completed review without cause.
4. Read what kickoff reads. Update plainly stale entries in Session, Pending user action, Deferred experiments and research, Investigations to review, Next action, and newest dated notes. Record today's verified end state, not this morning's. Give tomorrow one concrete next action. Preserve uncertainty and distinguish local verification from remote CI, visuals and reference fidelity.
5. Check statuses agree across `docs/development.md`, `docs/STATUS.md`, `docs/packages.md`, `AGENTS.md`, relevant blueprint sections, the active execution plan, reference evidence and session notes. Search changed wording with scoped `rg`. Run `python3 tools/roadmap.py`, then `python3 tools/roadmap.py --check`; a parse error (reworded heading, table or Later item) goes to the user. Do not duplicate rules or numeric design values into session notes when a link suffices.
6. Do not promote a proposal, rewrite a decision or invent history to make docs agree. If resolving disagreement requires a decision, list it for the user.
7. Check the working tree for stray root files, scratch output, your own background jobs, and unmerged branch work. Preserve other sessions' files and processes. Keep caches and local environment files untracked. Never clean destructively as part of wrap-up.
8. Show documentation changes, verification results and proposed commits grouped by purpose with short messages and branch name. Recap decisions made today, their effects, mistakes and ambiguous interpretations. Ask once for commit approval, using a selector tool when available. Do not stage unrelated user work.
9. Only after approval, commit the approved scope; session notes are committed in their own private repository under the same approval. If on `main`, include a proposed branch name in the approval request and obtain agreement before creating it. If no HEAD exists, explicitly identify this as the first commit. Never push, open a PR or merge as part of commit approval; those need separate explicit approval.
10. Finish in three lines: branch and last commit (or no commits yet), what awaits the user, and the first action kickoff will offer tomorrow. If commit approval is still pending, report that state without claiming a commit.
